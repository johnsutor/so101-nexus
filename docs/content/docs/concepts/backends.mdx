SO101-Nexus uses MuJoCo as its default simulation backend. Optional mjbatch and MuJoCo Warp backends add CPU and GPU batching for reinforcement learning. All three cover the same SO-101 tasks, with env IDs distinguished by the `MuJoCo`, `MJBatch`, and `Warp` prefixes. See [Environments](/docs/environments) for the ID list.

The MuJoCo backend is stable. The mjbatch and MuJoCo Warp backends are experimental: its API and physics may change between minor releases. See [Stability and versioning](/docs/api/stability).

## Vectorization

MuJoCo environments are vectorized through Gymnasium's standard `gym.vector.SyncVectorEnv` wrapper, which runs multiple environment instances on CPU.

The MuJoCo Warp backend instead batches simulation natively on the GPU. Construct any task with `gym.make_vec("WarpPickLift-v1", num_envs=N, device="cuda", vectorization_mode="vector_entry_point")`; reset and step return torch CUDA tensors of shape `(num_envs, ...)`.

Warp envs route the same composable state observation components as MuJoCo (see the [component table](/docs/concepts/observations) for the full list, which the two backends share). They also support `WristCamera` and `OverheadCamera` observation components, rendered in one batched ray-tracing pass on the simulation device. Cameras support RGB and depth, with per-world wrist-camera domain randomization. See [Depth observations](/docs/concepts/observations#depth-observations) for the output contract.

## CPU batching with mjbatch

Install the optional backend as described in [Installation](/docs/getting-started/installation#cpu-batch-backend-mjbatch), then construct a native vector environment:

```python
import gymnasium as gym
import so101_nexus.mjbatch
from so101_nexus import TouchConfig

env = gym.make_vec(
    "MJBatchTouch-v1",
    num_envs=16,
    num_threads=4,
    config=TouchConfig(),
)
obs, info = env.reset(seed=42)
env.action_space.seed(42)
obs, rewards, terminated, truncated, info = env.step(env.action_space.sample())
env.close()
```

`num_threads=0` lets mjbatch choose its native worker count automatically.
Reset and step return NumPy observations and arrays of rewards, terminations, and truncations.
Use `gym.make_vec`; these IDs have only a vector entry point.
The default autoreset mode is Gymnasium's `NEXT_STEP`. Pass `autoreset_mode="SameStep"`
for immediate resets with `final_obs` and `final_info`, or `"Disabled"` for explicit resets.
`max_episode_steps` overrides the registered episode limit; a negative value disables it.
The LeRobot EnvHub factory also accepts these IDs and uses same-step autoreset.

Each world uses an independent copy of the task configuration and model parameters,
including object selection, colors, wrist cameras, controls, and observation components.
`env.task_descriptions` returns the current instruction for each world.
The backend uses the CPU MuJoCo physics preset and honors `PhysicsConfig`.

mjbatch steps all but the final physics substep on its C++ thread pool.
The final substep runs on each task's MuJoCo data to preserve contact-force queries and
observation timing. Integration state and mutable model fields are synchronized each step.
Resets, rewards, observation assembly, inverse kinematics, and rendering run per world in Python.
PickAndPlace v2 uses scalar physics for every substep because its support evaluator needs
continuous contact checks. One-substep control intervals also use scalar physics.
Throughput depends on the task and batch size; this adapter does not claim a measured speedup.

Camera components support the same RGB and metric depth observations as CPU MuJoCo.
`env.render()` returns a tuple of per-world images using MuJoCo's rendering modes,
including `human` when a display is available. Rendering is per world and requires a
working OpenGL context. It is separate from mjbatch's physics thread pool.

## Render Modes

MuJoCo envs support Gymnasium `render_mode="human"`, `render_mode="rgb_array"`, and `render_mode="depth_array"`.
The depth render mode uses the same [metric depth contract](/docs/concepts/observations#depth-observations) as camera observations.
The rendered view is selected by [RenderConfig](/docs/api/configs#renderconfig).
Warp envs support `render_mode="rgb_array"` and `render_mode="depth_array"` through `gym.make_vec()`. Call `env.render()` to get a torch tensor on the simulation device: RGB has shape `(num_envs, height, width, 3)` and dtype `uint8`; metric depth has shape `(num_envs, height, width)` and dtype `float32`. Each call returns independent storage. Warp does not support `human` rendering and rejects unsupported modes.

Visualization renders only when requested, separately from policy camera observations. The render context is allocated on the first call. With `render_mode=None`, Warp adds no visualization camera or render context. Use [RenderConfig](/docs/api/configs#renderconfig) to select a view and optional placement ranges.

## Object Pools and the Batched Model

`WarpPickLift` and `WarpTouch` accept the same heterogeneous object pools as MuJoCo (`CubeObject`, `YCBObject`, `MeshObject`, plus `n_distractors`), `WarpPickAndPlace` accepts a carried-object pool plus one slot per `distractors` pool entry when `n_distractors > 0`, and `WarpStackCube` compiles one cube slot per configured color in `cube_a_colors`/`cube_b_colors` plus the same distractor slots. Each pool object is compiled as a freejoint slot, the per-world target (or, for pick-and-place and stack-cube, the role slots plus the sampled distractors) is selected at reset, and inactive slots are parked off-world for physics. A separate rendering view hides inactive slots below the floor in each world, excluding them from RGB, depth, and shadows while keeping active distractors visible. A pick-and-place target is only ever drawn from the carried pool, so `reset(options={"target_index": k})` indexes that pool alone.

Because all worlds share one compiled model, per-episode `geom_rgba` color randomization of a single object is unsupported. Distinct colored cube slots still give per-world color variation through selection (this is how `WarpStackCube` matches the MuJoCo backend's per-episode resampling of both cube colors), and the `WarpPickAndPlace` goal disc color is fixed to the first configured color.

Vectorized worlds may carry different tasks, so `env.task_descriptions` holds one string per world and `info["task_description"]` is returned from `reset()` and `step()`. `env.task_description` reduces to the shared string, or a generic family string when worlds differ.

## Physics Divergence

The historical CPU preset uses `implicitfast` and three NoSlip iterations. The Warp preset uses `implicit` and zero NoSlip iterations.
MuJoCo Warp 3.13 supports both integrators but does not implement NoSlip. Its device conversion also raises the native solver tolerance to `1e-6`.

[PhysicsConfig](/docs/api/configs#physicsconfig) selects supported physics configuration on both backends and preserves command timing when the timestep changes.
Matching configuration does not guarantee identical contacts or trajectories. The backends use different floating-point arithmetic and collision algorithms.
The optional [Warp box collision patch](/docs/getting-started/installation#warp-box-collision-patch) addresses the measured box contact mismatch in version 3.13.0.
Validate transferred policies on the target backend.

## Installation and Hardware

Install the backend with the `warp` extra, which needs an NVIDIA GPU and CUDA >= 12.8 for GPU execution. Warp has no ROCm/AMD support. To train on an AMD GPU you install the `rocm` extra instead, which affects only the MuJoCo backend's training loop; see [Installation](/docs/getting-started/installation).

## Objects

Both backends support `CubeObject`, `YCBObject`, and `MeshObject`, configured through the same object-pool fields (`objects`, `n_distractors`, and `distractors` on the pick-and-place and stack-cube families). See [Customization](/docs/concepts/customization) for the recipes and [Objects](/docs/api/objects) for the constructor reference.
