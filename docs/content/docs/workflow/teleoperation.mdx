---
title: Teleoperation
description: Drive a simulated SO-101 follower with a physical leader arm and record LeRobot v3 demonstration datasets.
---

SO101-Nexus ships a Gradio teleop recorder. A physical SO-100 or SO-101 leader arm drives a
simulated follower, and every approved episode is written to a LeRobot v3 dataset you can push
to the Hugging Face Hub. That dataset is the artifact the
[clone and reinforce](/docs/workflow/training) stages consume.

## Quickstart

```bash
uvx --from "so101-nexus[teleop]" so101-nexus teleop \
    --leader-port /dev/ttyACM0 \
    --seed 0
```

A Gradio UI opens in your browser. Most settings live in the UI; the CLI only takes
connection-level options. For a repeat-use install of the `teleop` extra, see
[Installation](/docs/getting-started/installation).

## Policy correction collection

Run a trained policy in the same viewer and take control when it needs correction:

```bash
uv run --extra teleop so101-nexus teleop \
    --leader-port /dev/ttyACM0 \
    --policy-path outputs/train/checkpoints/last/pretrained_model \
    --policy-fps 30 \
    --policy-device cpu
```

LeRobot checkpoints must include their preprocessor and postprocessor files.
The adapter loads the saved normalization statistics and resets cached actions on each handoff.
Set camera resolutions to match the checkpoint, and use its trained joint order and units.
Set the UI FPS to the checkpoint's action rate. Use `--policy-fps` to declare that rate
when it is absent from the checkpoint; initialization rejects mismatched rates.
Policy collection configures physics to advance exactly `1 / FPS` simulated seconds per
executed action. Physics substeps divide that interval exactly and remain no larger
than the configured physics timestep. Wall-clock inference latency can slow collection,
but it does not change simulated action spacing or dataset timestamps.
For chunked models, each `select_action` call consumes one action at that rate.
The model and its processor pipelines retain responsibility for chunk replay and history.
The default policy output is an absolute six-joint target.
For a checkpoint trained to predict deltas from current readback, add
`--policy-action-space joint_pos_delta`.
This flag describes model output; the UI action-space setting describes saved dataset actions.

### MolmoAct2 SO100/101

The original `allenai/MolmoAct2-SO100_101` package loads directly:

```bash
uv run --extra teleop --extra molmoact2 so101-nexus teleop \
    --policy-path allenai/MolmoAct2-SO100_101 \
    --policy-device cuda
```

See [Installation](/docs/getting-started/installation#extras) for model dependencies.
The loader selects continuous inference, the `so100_so101_molmoact2` normalization tag,
the checkpoint's gripper normalization, and LeRobot's documented legacy joint-frame
conversion for this package. Shoulder lift reverses direction about 90 degrees;
elbow flex shifts by 90 degrees. Recorded states and actions stay in follower coordinates.
The published rollout uses 30 Hz;
keep the UI FPS at 30. Overhead and side RGB views are supplied by default, matching
the published example's top and side views. The native image processor handles resizing.
For another original MolmoAct2 checkpoint, provide `--policy-norm-tag` and `--policy-fps`.
Its normalization metadata must describe SO101 joint order and absolute joint pose control.

Loading support does not establish task success or cross-calibration compatibility.
The default conversion follows LeRobot's SO100/101 migration recipe; a custom calibration
can require different signs or offsets. A custom factory can configure LeRobot's
`joint_signs` and `joint_offsets` and load its matching processors. Preserve the
training frame when fine-tuning.
See [LeRobot backward compatibility](https://huggingface.co/docs/lerobot/backwardcomp).

### Other SO101 policy checkpoints

The loader uses LeRobot's registered policy classes rather than a model allowlist.
LeRobot 0.6.1 checkpoints for ACT, Diffusion, SmolVLA, and other registered families
can use the same path when they have six SO101 joint channels, matching units and action
semantics, saved processor pipelines, and the appropriate optional model dependencies.
A policy family name alone does not establish checkpoint compatibility.
See [Installation](/docs/getting-started/installation#extras) for dependencies.

Use repeatable camera mappings when checkpoint names differ:

```bash
uv run --extra teleop so101-nexus teleop \
    --policy-path /path/to/so101/pretrained_model \
    --policy-fps 30 \
    --policy-camera overhead=front \
    --policy-camera wrist=wrist
```

Mappings rename collector inputs before preprocessing. Unmapped cameras remain available.
For original MolmoAct2 packages without camera-name metadata, supplied mappings select
the views passed to the model. Check the checkpoint's expected viewpoints as well as names.
Models with end-effector actions, padded outputs, or another robot's joint order need
a custom adapter rather than being accepted based on their action dimension alone.

### Intervention controls

1. Click **Start policy episode**. The policy controls the follower after the countdown.
2. Click **Pause and take control (T)** when correction is needed. Policy stepping stops immediately.
   The leader moves gradually to the follower's current pose, including the inverse wrist roll offset.
   Keep the leader clear while **Paused: aligning leader** is shown.
3. When alignment finishes or pauses, hold the physical arm and gripper.
   Check the support confirmation directly above C, then click **Start correction (C)**.
   If alignment needs attention, the button reads **Take control from this pose (C)**.
   The first correction action preserves the current simulated pose. Your movements
   from this point drive the follower, with pose differences compensated for every joint
   and the gripper. The simulation stays paused until you start correction.
4. Click **Resume policy (P)** to continue from the corrected state with a fresh prediction.
5. Repeat as needed, then review and approve the entire episode.

**Pause (H)** freezes simulation stepping and cancels an active leader synchronization.
Press each shortcut once; you do not need to hold it. After pausing, use T to align
the leader again before starting a correction, or P to resume the policy.
The controller panel shows remaining simulation time and steps. Paused time does not
consume this budget. Episodes end at Max Steps or after task success; **Stop and review episode**
ends recording and opens review.
The keyboard shortcuts work while the Record controls are visible and you are not typing in a field.
Slow model inference does not block a takeover request. A request takes effect between simulator steps.
Late predictions and cached chunks from before a handoff cannot control the follower afterward.
Simulation time freezes while paused or while inference or synchronization is pending;
these waits add no dataset frames.
This collector currently supports the simulated follower, not real-robot deployment.

Synchronization uses the calibrated leader motor bus, with body joints in degrees and the gripper in percent.
Targets ramp at up to 20 degrees per second for body joints and 40 percentage points per second for the gripper.
Before holding, each measured joint target must be acknowledged by that motor before
its torque is enabled. If a motor fails, holding is still attempted for the other joints;
the overall hold remains unconfirmed.
Default alignment tolerances are 10 degrees for body joints and 5 percentage points
for the gripper. Set `--leader-alignment-tolerance-deg` and
`--leader-gripper-tolerance-percent` to override them. Both must be positive and finite.
These tolerances guide alignment readiness; they do not block supported takeover
from a paused alignment pose.
Wrist roll uses circular angular distance, and its inverse offset wraps into the physical
single-turn range. During correction, wrist targets use the equivalent angle nearest
follower readback so crossing the angle boundary does not flip the simulated target.
An alignment timeout holds the measured physical pose and keeps the episode paused.
The controller panel lists the joints that did not reach their targets, including measured
and target positions. Hold the arm, confirm support beside C, and take control from
this pose. You can also press T to retry alignment or P to resume the policy.
Torque changes and synchronization reads and transmissions retry communication failures
up to three times through LeRobot.
A persistent motor communication error that prevents holding still ends recording.
Pausing, finishing an episode, and process cleanup also preserve motor torque.
Recording errors stay visible in Review, along with any failure to hold the leader.
If holding is unconfirmed, support the arm and gripper immediately.
These are target-command bounds, not guarantees of physical motor speed or successful holding
when motor communication or power fails.

To park the leader after recording stops, expand **Park or release the leader arm**.
Support or park the arm and gripper, check the parking confirmation, and click
**Release motors for parking**. This panel is not needed for normal takeover and
stays available in Review and Complete. Finalization and reinitialization require
this explicit release. The confirmation resets
after each handoff or release. Closing the process without releasing the leader preserves
motor torque; support and park the arm before disconnecting power.

### Custom model adapters

Use `--policy-factory my_project.policy:build_policy` for a custom model or remote inference client.
The no-argument factory returns an object with `select_action(batch)` and `reset()` methods.
This runnable scaffold holds the current pose; replace `select_action` with your model's prediction:

```python
class MyPolicy:
    def select_action(self, batch):
        return batch["observation.state"].copy()

    def reset(self):
        pass


def build_policy():
    return MyPolicy()
```

The batch contains an unbatched float32 `observation.state`, task text, and available
`observation.images.wrist`, `observation.images.overhead`, and `observation.images.side` arrays.
When available, `observation.environment_state` contains the privileged component vector.
Images use HWC uint8 RGB format. The state follows `SO101_JOINT_NAMES` order.
Body joints use degrees and the gripper uses 0 to 100 percent, matching follower readback.
Return a finite NumPy array or torch tensor of shape `(6,)` in the same order and units.
For delta output, use the policy action-space flag described above.
Map camera names, normalization, and any other model-specific inputs inside the adapter.
`reset()` must clear action chunks and recurrent history. All model calls run serially on an inference thread.
Custom factories own device selection; `--policy-device` applies to the built-in LeRobot loader.
A factory adapter may expose an integer `fps`; otherwise declare its rate with `--policy-fps`.

For another input device, `InterventionSession.request("human")`, `request("hold")`,
and `request("policy")` expose the same handoffs independently of Gradio.
The session accepts a synchronizer with `start(target)`, `tick()`, `cancel()`, and `release()`
methods and a `holding` property. `cancel()` stops alignment and holds the measured pose;
`tick()` keeps torque enabled after convergence. Only `release()` disables torque.
For a staged takeover, call `request("human", pause_after_sync=True)`, then
`start_correction()` after the operator supports the leader. It captures an anchor
before releasing torque, so correction starts from the current follower pose even
when alignment timed out. The anchor resets at each handoff. A direct `request("human")`
aligns and releases the leader, so its caller must obtain support confirmation first.
`end_episode()` holds the leader; `release_leader()` explicitly releases an idle leader.
`SOLeaderSynchronizer` provides the SO leader implementation.
These public objects are available from `so101_nexus`.

### Training on corrections

Collection records autonomous context and human corrections in one continuous episode.
Dataset fields identify which actions are expert supervision; the schema is described
[below](#recorded-dataset-format).
Do not train behavior cloning on autonomous actions as if they were human demonstrations.
Aggregate the original demonstrations with human-controlled targets from the new episodes.

For chunked policies, sample human-controlled starting frames and mask targets after the human segment ends.
The public helper works with NumPy arrays and torch tensors:

```python
import torch
from so101_nexus import intervention_chunk_mask

intervention_ids = torch.tensor([0, 1, 1, 0, 2])
mask = intervention_chunk_mask(intervention_ids, horizon=3)
```

Pass one episode at a time. Each mask row describes valid human targets for a chunk starting at that frame.
Zero marks autonomous frames; positive IDs distinguish correction segments.
Use the mask in your trainer's loss, and exclude autonomous starting frames from correction sampling.
The standard LeRobot training CLI does not automatically apply this helper or filter these fields.
Recovery and correction share the same human label in this initial collector.

## Hardware and the serial port

You need a physical SO-100 or SO-101 leader arm on USB and a host with access to its serial
port. If the device is not writable, fix permissions and confirm the port:

```bash
sudo chmod 666 /dev/ttyACM0
lerobot-find-port
```

The Configure step reports leader-port reachability before you fill in the rest of the form,
with a `Recheck Port` button, and blocks `Initialize Session` while the port is not ready. A
connect-time failure keeps the session alive on the Initialize step with recovery guidance, so
you can fix the port in another terminal and click `Retry Initialization`.

## Session flow

1. **Configure.** Pick the environment, robot type, episode count, FPS, camera resolutions,
   action space, countdown, dataset fields, Max Steps, and Success Hold.
2. **Initialize.** The app connects to the leader arm and creates the dataset.
3. **Record.** A countdown plays, then the simulation mirrors the leader arm. The live wrist,
   overhead, and side feeds render together in the UI.
4. **Review.** After each episode, the UI shows a synchronized replay of the available
   wrist, overhead, and side views, with camera labels and a joint-state plot.
5. **Approve or discard.** Accept to write the episode into the dataset, or re-record.
6. **Push.** When all episodes are done, check **Hub Repo ID** and push to the Hugging Face Hub.

The simulator stays loaded between episodes and resets with the current leader pose
and episode seed. Sessions with a config profile or factory rebuild the simulator
each episode so configuration changes still take effect.

The Complete step shows the original local recording directory and an editable **Hub Repo ID**.
You can change the upload destination to `your-username/dataset-name`, including after an upload failure.
The local recording stays in its original directory.

If you forgot your username or used the wrong namespace, correct **Hub Repo ID** on the Complete step.
Then click **Push to Hub** again.
You do not need to record the episodes again.

## Cameras and recorded fields

Wrist, overhead, and side cameras are captured on every step and selected for the dataset by
default. Live previews update at up to 10 Hz; recorded frames use the configured FPS.
Wrist and overhead observations are wired automatically, and their width and height
sliders set the image resolutions. The side view uses the overhead resolution and the
simulator's render camera. Its azimuth is randomized between 105 and 115 degrees, and its
elevation between -27 and -23 degrees, on each seeded reset. A config factory can override
these ranges through `RenderConfig`, including equal bounds for a fixed view.
The default side distance adapts to the sampled angles and spawn region.
See [automatic side framing](/docs/api/configs#renderconfig) for distance overrides.

Under **Advanced Settings, Dataset fields**, a checkbox group selects which fields are
persisted; deselecting an optional field drops it from the declared feature schema and from
every recorded frame. `observation.state`, `action`, `reward`, `success`, `done`, and `task`
stay forced on because LeRobot datasets require them for policy training and task indexing.

### Recorded dataset format

Datasets use the LeRobot v3 SO follower schema. Always present:

- `observation.state`: follower readback, 6D
- `action`: executed joint targets, 6D (absolute by default)
- `reward`: scalar transition reward from the same environment step as `action`
- `success` and `done`: episode success and termination flags
- `task`: language description, from LeRobot v3 metadata

Policy correction datasets additionally require `is_intervention` (float32, 0 or 1) and
`intervention_id` (int64, 0 for autonomy, positive per human segment).
The recorder preserves the executed follower command after limiting, paired with pre-action readback.
When the UI selects `joint_pos_delta`, correction datasets store target minus pre-action readback.
Ordinary teleop delta datasets retain their frame-to-frame target differences.
Episode reproducibility metadata includes the policy path or factory, device, camera mappings,
normalization options, effective FPS, and policy action convention.
A local checkpoint path identifies its source; it does not capture a hash of mutable weights.

Optional, on by default: `observation.images.wrist`, `observation.images.overhead`,
`observation.images.side`, and
`observation.environment_state` (privileged low-dim state: TCP and object pose, grasp,
offsets).

Body joints are stored in LeRobot degree units and the gripper in `RANGE_0_100` percent,
matching `sim_so_follower` and SO100/SO101 MolmoAct2 normalization. `observation.state` is
simulated follower readback, not the leader echo.

On finalize, before any Hub push, the app writes the environment id and customization
overrides to `meta/so101_nexus_env.json` inside the dataset. That file is itself a valid
[config profile](#config-profiles), so `--env-config-profile meta/so101_nexus_env.json`
reproduces a recording's environment. It captures UI and CLI overrides only; a separate
`--env-config-profile` used at record time is not merged in.

For pick-and-place v2, both the teleop recorder and `RolloutRecorder` also save
`meta/placement_contracts/episode_NNNNNN.json`.
Each file stores the episode's [resolved evaluator contract](/docs/environments#evaluator-diagnostics).
The recorder refuses to overwrite an existing contract.
It does not add these diagnostics to policy features or relabel legacy episodes.
See the [placement contract](/docs/environments#success-conditions) for benchmark migration rules.

The recorder saves `meta/reproducibility/episode_NNNNNN.json` for each approved episode.
The effective episode seed is the base seed plus the approved episode index.
A discarded episode keeps its seed when you record it again.
Each file also stores the task description and the initial simulator state.
The state includes robot and object positions, velocities, controls, mocap poses, camera transforms, and sampled colors.
These snapshot fields preserve native simulator units for replay: hinge angles use radians,
translations use meters, and camera FOV uses degrees. User-facing joint actions still use degrees.

For environments that expose rendering metadata, the top-level `rendering` field records
camera quality and allocated renderer details after the recording finishes.
`RolloutRecorder` saves the same sidecar path with `seed` and `rendering` fields when it writes a dataset.
It also returns the metadata in `EpisodeResult.info["rendering"]` without a dataset.
Lazy visualization cameras appear after their first render.
See [RenderingQuality](/docs/api/configs#rendering-quality) for profile selection and hardware limits.

On first recording the app creates a simulator-only calibration file at
`$HF_LEROBOT_CALIBRATION/robots/sim_so_follower/teleop_sim.json`, or under the LeRobot default
calibration root when that variable is unset. No physical follower calibration is needed.

## Environment customization

Teleop uses the same typed config objects as the regular Gymnasium API. The recorder starts
from the selected environment's default config, applies UI, profile, and factory overrides,
then wires the camera observations required for recording.

**Advanced Settings** exposes the common options. Turn on `Apply Environment Customization` to
enable them; leave it off to use the default config unchanged.

| Option | Effect |
| --- | --- |
| `Pick Object Pool` | Built-in cube and YCB objects for pick tasks |
| `Minimum Distractors`, `Maximum Distractors` | Inclusive count bounds for tasks that support distractors. Equal values give a fixed count; see [sampling and pool limits](/docs/api/configs#pickconfig) |
| `Ground Colors`, `Robot Colors` | Sampled per reset when multiple colors are selected |
| `Spawn Min Radius`, `Spawn Max Radius`, `Spawn Angle Half Range (deg)` | Spawn-region controls shared by supported tasks |
| `Reset Settle Frames` | No-op frames after reset before the first recorded frame (default 5), applied before cameras are wired |
| `Pick-and-Place Cube Colors`, `Pick-and-Place Target Colors` | Sampled cube and target colors |
| `Stack Cube A Colors`, `Stack Cube B Colors` | Sampled colors for the two cubes |
| `Max Steps` | Overrides the episode's step cap |
| `Success Hold (s)` | Seconds to keep recording after success before auto-stopping (default 0.5, 0 stops immediately) |

Options that do not apply to the selected environment are ignored: pick-object settings apply
to `PickConfig`, pick-and-place colors to `PickAndPlaceConfig`, stack-cube colors to
`StackCubeConfig`. Field names and defaults are in [Config reference](/docs/api/configs).

### Config profiles

Use a profile for a repeatable recording setup. Profiles may be JSON or TOML and are merged in
this order, with later sections overriding earlier ones: flat top-level override keys,
`common`, the matching task section (`pick`, `pick_and_place`, or `stack_cube`), then
`envs.<env_id>`.

```toml
[common]
ground_colors = ["gray", "white"]
robot_colors = ["yellow"]
spawn_min_radius = 0.15
spawn_max_radius = 0.25
reset_settle_frames = 5

[pick]
min_distractors = 0
max_distractors = 2
objects = [
  { type = "cube", color = "green" },
  { type = "ycb", model_id = "009_gelatin_box" },
  { type = "ycb", model_id = "032_knife" },
]

[pick_and_place]
cube_colors = ["red", "green"]
target_colors = ["blue"]

[stack_cube]
cube_a_colors = ["red", "orange"]
cube_b_colors = ["blue", "green"]

[envs.MuJoCoPickLift-v1]
spawn_angle_half_range_deg = 60.0
```

```bash
uv run so101-nexus teleop \
    --leader-port /dev/ttyACM0 \
    --env-config-profile teleop-profile.toml
```

The profile object schema matches the classes in [Scene Objects](/docs/api/objects). String
specs such as `cube:blue` and `ycb:009_gelatin_box` work for built-in object choices. Mesh objects
use mapping syntax because file paths may contain separator characters:

```toml
[[pick.objects]]
type = "mesh"
name = "custom widget"
collision_mesh_path = "/path/to/collision.stl"
visual_mesh_path = "/path/to/visual.obj"
mass = 0.02
scale = 1.0
```

### Config factories

For advanced setups, pass a Python factory with
`--env-config-factory my_project.teleop_configs:build_config`. It receives
`(env_id, base_config)` and may return a config object:

```python
from so101_nexus import CubeObject, PickConfig, YCBObject


def build_config(env_id, base_config):
    return PickConfig(
        objects=[CubeObject(color="green"), YCBObject("009_gelatin_box")],
        n_distractors=1,
    )
```

It may also return a `dict` of `gym.make` kwargs. If the dict includes `"config"`, teleop still
wires the recording cameras after the factory runs.

### Custom environments

Custom environments must be registered with Gymnasium before teleop builds the dropdown.
Import the registration module and list the environment ID:

```bash
uv run so101-nexus teleop \
    --leader-port /dev/ttyACM0 \
    --env-module my_project.envs \
    --extra-env-id CustomPick-v1
```

A custom environment should accept SO-100/SO-101 six-joint actions in the standard joint order,
expose current qpos through `_get_current_qpos()`, and return camera observations compatible
with the recording cameras. Teleop captures all three views even when a dataset field is
deselected. Custom environments must support `render_mode="rgb_array"` and return an RGB
side view from `render()` at the overhead image resolution. A config without `RenderConfig`
must set that resolution itself. If the unwrapped environment exposes `task_description`,
teleop records it as the required LeRobot `task` field.

`lerobot-find-port`, then retry initialization in the same browser session. The UI stays on the
Initialize step and shows recovery guidance instead of forcing a restart.

For teleop this is usually non-fatal: the recorder renders the simulation feed offscreen as
`rgb_array`, not through the MuJoCo human viewer, so recording works even when native window
